# smarli. Blueprints — Docker Home Assistant test environment

A local, disposable Home Assistant instance used to test the cover blueprints and the `ha-packages` packages together at
**runtime**, because `check_config` catches almost none of what actually breaks: Jinja errors,
wrong filter arity, non-boolean template conditions and event-ordering races all pass config
validation and fail only when a template renders.

The environment lives **in this repo** under `test/runtime/` (since 2026-10-29). One command builds
it on any Windows machine with Docker Desktop, Git and a checkout of
[`ha-packages`](https://github.com/smarli-AG/ha-packages) next to this repo. This document holds
the hard-won facts about it.

---

## Layout

```text
test/runtime/
  bootstrap.ps1          builds the instance from scratch (see "Rebuilding from scratch")
  docker-compose.yml     one service; container, port and ha-packages folder from env (see below)
  run-short.ps1          core suites, ~20 min
  run-long.ps1           schedule suites, ~35 min
  check-config.ps1       check_config on 2024.10 and 2025.4
  lib/ha.ps1             helpers (HA-Call, HA-Event, HA-State, HA-Tracker, HA-Apply, ...) — dot-source before use
  lib/lib-test.ps1       T-Check/T-Note (results log), cover helpers, logs the repo refs once per run
  lib/lib-test2.ps1      timeline sampling (Sample-Cover, Watch-Cover)
  tests/test-*.ps1       the runtime test suite (see below)
  skeleton/              configuration.yaml, virtual.yaml, mint.py — copied into .state by bootstrap
  .state/                git-ignored: everything the instance writes
    config/              the HA config directory, bind-mounted to /config
      automations.yaml   test rig + blueprint instances + resolver stubs, generated by HA-Apply
      custom_components/ virtual, swissweather (downloaded by bootstrap, pinned)
    .token               long-lived access token (~1 year), used by every helper
    .onboarding          the test login (user:password)
    results.log          every PASS/FAIL/REFS line
```

**Mounted, not copied.** `docker-compose.yml` mounts this repo's `automation/` folder read-only as
`/config/blueprints/automation/smarli/`, and the `ha-packages` checkout's `packages/` read-only as
`/config/packages/`. The instance therefore always runs what is checked out. Every test run logs
both refs (branch and commit) to `results.log` and warns when either tree has uncommitted changes.

Overrides, read by `lib/ha.ps1`, `bootstrap.ps1` and `docker-compose.yml` alike:

| Variable          | Default                              | Use                                         |
| ----------------- | ------------------------------------ | ------------------------------------------- |
| `HA_PORT`         | `8123`                               | a second instance next to the first          |
| `HA_CONTAINER`    | `smarli-ha-test`                     | container and compose project name           |
| `HA_PACKAGES_DIR` | `<repo>\..\ha-packages\packages`     | another `ha-packages` checkout               |
| `HA_VERSION`      | `2025.4`                             | the HA image tag (compose only)             |

Only one `.state` exists per checkout, so a second instance needs a second checkout.

## Daily use

```powershell
. .\test\runtime\lib\ha.ps1      # also fixes the PATH: docker is not on the PATH tool shells start with
.\test\runtime\run-short.ps1
.\test\runtime\tests\test-fingerprint.ps1
```

Start, stop, pin a version (from `test/runtime/`):

```powershell
docker compose -p smarli-ha-test up -d
docker compose -p smarli-ha-test down
$env:HA_VERSION="2024.10"; docker compose -p smarli-ha-test up -d    # another image
docker inspect smarli-ha-test --format '{{.Config.Image}}'
```

After any restart, wait for the API before testing — HA answers the port long before it is ready.
`Wait-HA` in `lib/ha.ps1` does this (polls `/api/onboarding`, then 15 s for entities to register).

## Deploying repo changes

Nothing to copy: edit in the repos, then make HA reload what changed.

- **Blueprint** (`automation/*.yaml`): `HA-Call automation reload`.
- **Package** (`ha-packages/packages/*.yaml`): the matching YAML reload (`script reload`,
  `template reload`, `automation reload`) or `docker restart smarli-ha-test`. Reloading
  automations alone does not reload a package's scripts or templates.
- **Test automations** (`HA-Apply` in `lib/ha.ps1`): written to `.state/config/automations.yaml`
  and reloaded by `HA-Apply` itself.

Check `REFS` in `results.log` before trusting a run: it shows which branch and commit of each repo
was mounted, and whether either had uncommitted changes.

## Config check on both floors

The floor of `cover_DayNight.yaml` is **2025.4.0** since 3.1.2 (the `md5` filter of the settings
fingerprint does not exist before 2025.4). Other blueprints still declare 2024.10.0, so keep
checking both versions: on 2024.10 the cover instances are expected to be rejected, nothing else
may fail.

```powershell
.\test\runtime\check-config.ps1                    # 2024.10 and 2025.4
.\test\runtime\check-config.ps1 -Versions 2026.10
```

It runs against a scratch copy of `.state/config` with the same mounts as the instance. Three
traps it handles: **without `--info all` check_config prints nothing but the header**; the output
carries **ANSI colour codes**; and **a rejected blueprint instance does not fail the check** — it
exits 0 with "Successful config" and only logs `generated invalid automation ...` (this is how the
missing `md5` filter on 2024.10 showed up), so the script greps for `invalid automation` too. A
read-only (`:ro`) config mount adds harmless registry-write errors, hence the scratch copy.

## What is installed

| Component                                                                       | Why it is there                                                                                                      |
| ------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `default_config`                                                                | full stack — API, websocket, recorder, frontend                                                                      |
| `demo`                                                                          | position and binary covers, but they **never report `opening`/`closing`**                                            |
| **hass-virtual** (twrecked, tag `v0.9.4`, GPL-3.0)                              | the only covers that simulate travel _with_ `opening`/`closing` states, which is what makes the settle loop testable |
| **hass-swissweather** (izacus, 1.3.2 = commit `41279cc`, Apache-2.0)            | a real MeteoSwiss weather entity with hourly forecasts, for the weather-block path                                   |

Both are **downloaded by `bootstrap.ps1`** at the pinned ref (`$COMPONENTS` there), not vendored,
so no third-party code lives in this repo. swissweather 1.3.2 has no tag, hence the commit.

**hass-virtual needs a patch.** v0.9.4 calls `verify_domain_control(COMPONENT_DOMAIN)` in two
places in `__init__.py`; the correct signature is `verify_domain_control(hass, COMPONENT_DOMAIN)`.
Without it, setup fails. Covers are declared new-style in `virtual.yaml` under the group
`imported`, with a bare `virtual:` in `configuration.yaml`. **On the first boot the import flow
overwrites `virtual.yaml` with `devices: {}`** when the file already exists: write it after the
first boot (or before `virtual:` is added), then restart. Each cover needs `name: vfast` (etc.)
and `class: shutter` to get the entity id `cover.vfast`.

**hass-swissweather** is configured headlessly by posting to `/api/config/config_entries/flow`
with postcode `8001`; the station is optional because `condition` comes from the forecast rather
than the station. It reports `supported_features: 3` (daily + hourly), so the blueprint's
FORECAST_HOURLY bit-2 guard passes and `weather.get_forecasts` returns real data.

## Gotchas that have each cost a debugging session

- **Any REST or WebSocket service call carries a `user_id`**, so manual detection reads it as a
  human acting and the cover self-suspends. To drive an _automated_ (contextless) move, arm the
  `test_mover` rig (`HA-Move`), or publish an intent through a stub. After any
  bare `cover.*` call, clear the resulting `*::suspension` keys before asserting anything.
- **Demo covers cannot test the settle loop.** Position covers ramp with the state stuck on `open`;
  binary covers jump instantly. Neither ever reports `opening`/`closing`, so the settle loop audits
  mid-ramp and false-suspends. Use the virtual covers.
- **Calling `script.smarli_cover_resolve` over REST taints the move too.** Its cover commands carry
  the token's `user_id` with no `parent_id`, so `smarli_cover_command_check` suspends the covers
  (correct per "Who counts as a person"). Drive the resolver through an event-triggered stub
  automation instead; the stubs accept `ts` and `transition` overrides in the event data.
- **A template cover shows the position it was commanded to.** `async_set_cover_position` stores
  the commanded position unconditionally, and the cover shows it at its next state write until
  the position template's *result* changes. In a tilt-first move that write is the first tilt
  report, so `cover.silent` claimed "at target" for the whole tilt phase and the old settle loop
  passed a test it should have failed. Its position template therefore adds `tilt / 100000`: the
  result changes on every tilt report and the real position wins. Re-rendering alone is not
  enough — an unchanged result never reaches the cover.
- **The history API drops attribute-only changes of covers**, even with
  `significant_changes_only=false`. To see a cover's position over time, sample
  `/api/states/<cover>` live instead.
- **`check_config` does not catch runtime Jinja errors.** Debug templates live instead:
  ```powershell
  Invoke-RestMethod -Uri "$HA_BASE/api/template" -Method Post -Headers (HA-Headers) -Body (@{template='{{ ... }}'} | ConvertTo-Json -Compress) -ContentType "application/json"
  ```
- **`last_changed` is the _latest_ transition, not the start of a move.** Measuring when covers
  began moving needs the history API: `/api/history/period/<iso8601>?filter_entity_id=cover.vfast,cover.vslow`,
  then take each entity's first `closing`/`opening` entry.
- **The tracker cannot delete a namespace.** `smarli_tracker_remove` removes a key and always
  re-inserts the (possibly empty) namespace bucket. Emptied namespaces persist; assert on keys.
  They can be purged out-of-band by POSTing a cleaned `data` attribute to
  `/api/states/sensor.smarli_automation_tracker`.
- **The tracker survives restarts via `.storage/core.restore_state`, not the recorder**, so
  excluding it from the recorder is safe and does not lose state across a restart.
- **PowerShell here is 5.1**: no `&&`/`||` chaining, no ternary, no `if(){}` as an expression.
  Chain with `;`, precompute into variables, and use `-join`.
- **`Get-Date -UFormat %s` returns a local-time epoch**, off by the UTC offset (7200 s in CEST).
  Use `([datetimeoffset](Get-Date)).ToUnixTimeSeconds()` when comparing against tracker timestamps.
- **A bare REST `cover.*` call only proves layer 1, never layer 2.** Every REST/WS call carries the
  token's `user_id`, so the _first_ state write it causes is always tainted — that write can never
  land in the "neither `user_id` nor `parent_id`" ambiguous case layer 2 exists for. To get a
  genuinely contextless write without real hardware, use HA's own context-recency rule instead:
  `homeassistant.helpers.entity.CONTEXT_RECENT_TIME_SECONDS` (confirmed **5s** on this image via
  `docker exec smarli-ha-test python3 -c "import homeassistant.helpers.entity as e; print(e.CONTEXT_RECENT_TIME_SECONDS)"`)
  nulls an entity's stored service-call context once it's older than that, so any subsequent
  internal `async_write_ha_state()` (e.g. a virtual cover's travel-simulation tick) is written with
  a **brand-new, contextless** `Context()`. Command a REST move on a **slow** cover (`vslow`, 16 s
  travel — comfortably past the 5 s cutoff), clear whatever suspension the tainted first tick
  produces, then wait past t+5s with no marker present: any later tick is the real ambiguous case,
  and there is nothing else that can have written the resulting suspension. See
  `test-r2-layer2-contextless.ps1`.
- **Forcing a schedule with `weather_events` values outside the blueprint's `select` selector list
  works at `use_blueprint:` scope** (config-check and runtime both accept it — selector `options`
  aren't enforced outside the UI dropdown), but don't rely on it: real weather rarely reports the
  _exact_ option string you'd need to test the "currently matches" branch, and a technician can
  only ever pick from the 9 listed options anyway. Prefer a real listed option (`rainy`, `windy`,
  …) when the live condition happens to allow it.

## Test suite

All in `test/runtime/tests/`. `run-short.ps1` runs the core suites, `run-long.ps1` the schedule
suites (`test-daynight` to `test-time-earliest` below); `results.log` in `.state/` collects every
PASS/FAIL line with a `REFS` line per run.

**The tests do not depend on the real time of day.** The blueprint has no time or sun trigger,
only a per-minute heartbeat; what depends on the clock is what each heartbeat computes. Two
fixtures in `lib/lib-test.ps1` move the instance instead of the clock (a faked clock would confuse
HA's scheduler, which runs on the monotonic clock):

- **`T-LocalNoon`** (on every test start) sets a whole-hour time zone (`Etc/GMT±N`) that puts HA's
  local time near midday. Schedule times like "now + 40 s" then never cross midnight —
  `today_at('00:01')` would read as this morning and fire at once.
- **`T-SunPhase night|day`** moves the longitude until solar midnight (or noon) is now, so the
  brightness method's arming windows (close from sunset − 60 min, open from sunrise − 60 min to
  sunset − 60 min) are where the test needs them. `T-SunHome` moves it back, in a `finally`.
  The 60 min offset is a fixed blueprint variable, not an input, so it cannot be widened instead.
  For sun-method tests, the `sunset_offset`/`sunrise_offset` inputs could do it: HA does not check
  input values against the selector range.

Always take clock times from HA (`HA-At`), never from the host: the host stays on Zurich time.

**No core settings in `configuration.yaml`.** Name, location, time zone and units are stored
(`bootstrap.ps1` sets them with `config/core/update`). Set in YAML, they would override the stored
values at every start, so a test that moves the time zone or the sun and then restarts HA
(`test-restart-selfheal`) would wake up in Zurich daylight — this is what first broke its
brightness case.

**Tests check only their own covers.** The sun instance stays on, and `T-Prep` drops its intent,
so it re-commands the garage door at its next per-minute heartbeat (the `transition` flag sends
even an unchanged position). A check for leftover markers or suspensions must therefore name the
test's own covers, not match `*::moving_*` across the whole tracker.

**A 5 s heartbeat makes the schedule tests fast.** `Build-Automations` adds a custom trigger
`time_pattern seconds: "/5"` with `id: heartbeat` to the time and brightness instances — the
blueprint's heartbeat branch only checks the id. With second-precision times (`HA-At`), an
earliest-close run takes about a minute instead of four. The real per-minute trigger stays; the
sun instance keeps only that one, so `test-daynight` covers it, and `test-restart-selfheal`
uses `HA-Apply -RealHeartbeat`, because a 5 s heartbeat would heal its stale state before the
restart.

**Keep the PC awake** for a full run: Modern Standby pauses Docker, and a run then simply stops
until the PC wakes.

## Rebuilding from scratch

Needs Docker Desktop (WSL2 backend; no sign-in for local containers), Git, and the
[`ha-packages`](https://github.com/smarli-AG/ha-packages) repo cloned **next to** this one (or
`HA_PACKAGES_DIR` set). Then, from `test/runtime/`:

```powershell
.\bootstrap.ps1            # ~5 minutes, two boots
.\bootstrap.ps1 -Force     # stop the instance, delete .state, build again
```

What it does, in order — each step encodes a fact that once cost a debugging session:

1. Copies `skeleton/configuration.yaml` and `mint.py` into `.state/config`, and writes
   `automations.yaml` with `Build-Automations`. **Not** `virtual.yaml` yet (see the hass-virtual
   note above).
2. Downloads the two custom components at their pinned refs and applies the
   `verify_domain_control(hass, …)` patch to hass-virtual. `-ComponentsFrom <dir>` copies them
   from a local folder instead.
3. First boot, then onboarding: `POST /api/onboarding/users`, `/auth/token`, then `core_config`,
   `analytics` and `integration` — all four, or the instance stays half-onboarded. The login goes
   to `.state/.onboarding`.
4. Access tokens expire in 30 minutes, so it mints a long-lived one inside the container
   (`mint.py`, a unique client name per run — re-using a name fails with
   `ValueError: <name> already exists`) and saves it to `.state/.token`.
5. Sets the core settings (Zurich, `Europe/Zurich`, metric) through `config/core/update`, and
   drives the swissweather config flow with postcode `8001`.
6. Writes `virtual.yaml`, restarts, turns the time and brightness instances off, and checks that
   every entity the suite needs exists.

It refuses to run when `.state/config` exists (also a half-built one: onboarding cannot run
twice), and when the port is in use.
